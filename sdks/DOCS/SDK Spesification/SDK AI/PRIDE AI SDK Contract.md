# PRIDE AI SDK Contract

**Version:** 1.0.0
**Status:** Draft
**Category:** SDK Contract
**Document ID:** PRIDE-AI-SDK-CONTRACT
**Related Specification:** PRIDE SDK Specification
**Related Standard:** PRIDE SDK Code Standard

---

# 1. Purpose

This document defines the public contract of the PRIDE AI SDK.

The contract defines how an executable task requests an Artificial Intelligence capability, how the request is represented, how execution results are returned, and how failures are represented.

The contract is independent from:

* AI provider.
* AI model.
* AI runtime.
* Programming language.
* Framework.
* Library.
* Transport mechanism.
* Implementation architecture.

---

# 2. Contract Boundary

The AI SDK contract exists between:

```text
Executable Task
       │
       ▼
   AI SDK Contract
       │
       ▼
 AI SDK Implementation
       │
       ▼
 AI Configuration
       │
       ▼
 AI Implementation
       │
       ▼
External AI System
```

The executable task only interacts with the public AI SDK contract.

Implementation-specific behavior shall not cross the contract boundary.

The AI SDK is the canonical programming interface between executable tasks and AI Modules.

---

# 3. Contract Principles

The AI SDK Contract follows these principles:

1. Capability-oriented requests.
2. Implementation independence.
3. Explicit configuration selection.
4. Standardized responses.
5. Standardized errors.
6. Stateless SDK execution.
7. No automatic implementation substitution.
8. No provider-specific behavior in the public contract.
9. No memory ownership inside the AI SDK.
10. Forward compatibility.

---

# 4. AI Request

An AI Request represents one request to execute one standardized AI Capability.

Logical structure:

```text
AIRequest

├── request_id
├── capability
├── input
└── metadata
```

---

## 4.1 request_id

`request_id` uniquely identifies the execution request.

Requirements:

* Required.
* Unique within the applicable execution context.
* Generated by the request originator.
* Returned in the corresponding response or error.

The SDK shall preserve the request identifier throughout execution.

The request identifier shall not contain provider-specific information.

---

## 4.2 capability

`capability` identifies the standardized AI Capability being requested.

Examples of standardized capabilities include:

```text
conversation
reasoning
planning
generation
vision
audio
embedding
structured_output
tool_calling
streaming
```

These capability categories are established by the AI Capability architecture.

The request shall reference a capability rather than an AI provider or model.

The executable task shall not select the underlying implementation through the capability field.

---

## 4.3 input

`input` contains the capability-specific input.

The structure of `input` is determined by the contract of the requested capability.

The AI SDK shall not redefine the internal logical schema of every capability.

Conceptually:

```text
AIRequest
    │
    ├── capability = reasoning
    │
    └── input = reasoning-specific input
```

or:

```text
AIRequest
    │
    ├── capability = generation
    │
    └── input = generation-specific input
```

This allows capabilities to evolve independently while the AI SDK maintains one common request envelope.

---

## 4.4 metadata

`metadata` contains execution metadata required by the platform or the capability.

Metadata is not Artificial Intelligence memory.

Metadata may provide contextual information required for execution.

Examples may include:

* Execution context identifiers.
* Task identifiers.
* Correlation information.
* Capability-specific execution metadata.

The exact metadata fields may evolve independently from the AI implementation.

The AI SDK shall not use metadata as a replacement for the Memory SDK.

---

# 5. AI Response

A successful execution returns an AI Response.

Logical structure:

```text
AIResponse

├── request_id
├── capability
├── output
└── metadata
```

---

## 5.1 request_id

The response shall contain the `request_id` of the corresponding request.

This allows the consumer to associate a response with its originating request.

---

## 5.2 capability

The response shall identify the capability that produced the result.

The returned capability shall correspond to the requested capability.

The implementation shall not silently transform one requested capability into another capability.

---

## 5.3 output

`output` contains the standardized result of the requested capability.

The output structure is capability-specific.

For example:

```text
Conversation
    ↓
Conversation Output
```

```text
Embedding
    ↓
Embedding Output
```

```text
Structured Output
    ↓
Structured Output Result
```

The AI SDK shall expose the standardized capability result rather than an implementation-specific provider response.

---

## 5.4 metadata

Response metadata may contain standardized information relevant to the execution.

Implementation-specific provider data shall not be exposed unless explicitly defined as part of the applicable contract.

---

# 6. AI Error

A failed execution shall return a standardized AI SDK Error.

Logical structure:

```text
AIError

├── request_id
├── error_code
├── message
└── metadata
```

---

# 7. Standard Error Categories

The AI SDK shall provide a unified error model.

The following categories are established by the existing AI architecture:

```text
CONFIGURATION_ERROR
AUTHENTICATION_ERROR
PERMISSION_ERROR
CONNECTION_ERROR
TIMEOUT_ERROR
CAPABILITY_UNSUPPORTED
RATE_LIMIT
RUNTIME_ERROR
UNKNOWN_ERROR
```

These categories are intended to normalize implementation-specific failures before they reach executable tasks.

---

## 7.1 CONFIGURATION_ERROR

Returned when the selected AI Configuration is invalid, unavailable, disabled, or otherwise unsuitable for execution.

---

## 7.2 AUTHENTICATION_ERROR

Returned when the selected implementation cannot authenticate using the credentials associated with the active AI Configuration.

---

## 7.3 PERMISSION_ERROR

Returned when execution is not permitted by the applicable AI system or platform rules.

---

## 7.4 CONNECTION_ERROR

Returned when the selected implementation cannot establish the required connection.

---

## 7.5 TIMEOUT_ERROR

Returned when execution exceeds the permitted execution time.

---

## 7.6 CAPABILITY_UNSUPPORTED

Returned when the active AI implementation does not support the requested capability.

AI implementations declare their supported capabilities, while executable tasks request standardized capabilities through the AI SDK.

---

## 7.7 RATE_LIMIT

Returned when the selected AI implementation refuses execution because an applicable usage limit has been reached.

---

## 7.8 RUNTIME_ERROR

Returned when the AI implementation encounters an execution failure that cannot be represented by a more specific standardized category.

---

## 7.9 UNKNOWN_ERROR

Returned when the failure cannot be reliably classified.

---

# 8. Error Message

The `message` field provides a human-readable explanation of the failure.

Messages shall:

* Be understandable to the consumer.
* Avoid exposing unnecessary implementation internals.
* Not expose credentials.
* Not expose private provider information.
* Remain secondary to the standardized `error_code`.

Consumers shall use `error_code` for programmatic error handling.

---

# 9. AI Configuration Resolution

The AI SDK shall execute requests using the currently active AI Configuration.

The AI SDK shall not automatically select another configuration.

The logical execution sequence is:

```text
AI Request
    ↓
Validate Request
    ↓
Load Active AI Configuration
    ↓
Resolve Referenced Implementation
    ↓
Execute Capability
    ↓
Normalize Result
    ↓
Return AI Response
```

This follows the established AI execution lifecycle.

---

# 10. Configuration Boundary

The AI SDK consumes the active AI Configuration.

The AI SDK does not own configuration creation or configuration ownership.

An AI Configuration is user-owned and identifies the implementation and execution parameters required for one AI connection.

The SDK shall therefore:

* Read the active configuration.
* Use its implementation reference.
* Use its required execution information.
* Execute through the referenced implementation.

The SDK shall not:

* Create hidden configurations.
* Replace configurations.
* Modify user configurations.
* Automatically switch configurations.

These rules preserve user control.

---

# 11. Capability Resolution

Executable tasks request capabilities.

They do not request:

* Providers.
* Models.
* Runtime names.
* Vendor APIs.
* Transport protocols.

The implementation associated with the active configuration determines whether the capability is supported.

If supported:

```text
Capability Request
       ↓
Execution
       ↓
Response
```

If unsupported:

```text
Capability Request
       ↓
CAPABILITY_UNSUPPORTED
```

---

# 12. Statelessness

The AI SDK is stateless.

The SDK shall not manage:

* Long-term memory.
* User history.
* Persistent conversation state.
* Context storage.
* Session synchronization.

Conversational or contextual information required for an AI request is supplied by higher-level platform components.

The AI SDK therefore does not replace the Memory SDK.

---

# 13. Memory Separation

AI SDK metadata and AI input shall not be interpreted as platform memory ownership.

Memory operations remain governed by the Memory Architecture.

The AI SDK shall not:

* Directly own platform memory.
* Define Memory Capabilities.
* Define Memory Storage.
* Replace the Memory SDK.
* Create an alternative memory access path.

The AI SDK may receive contextual information required for AI processing, but that does not transfer memory ownership to the AI SDK.

---

# 14. Implementation Independence

The public contract shall not expose:

* Provider-specific request formats.
* Provider-specific response formats.
* Provider-specific authentication structures.
* Provider-specific transport structures.
* Provider-specific runtime objects.

The implementation translates the standardized AI SDK request into implementation-specific operations and normalizes the result back into the SDK response format.

---

# 15. Provider and Model Selection

The AI SDK Contract does not expose provider or model selection as a consumer-level implementation mechanism.

Provider and model details remain inside the AI Configuration and associated implementation.

A consumer therefore requests:

```text
capability = reasoning
```

rather than:

```text
provider = example-provider
model = example-model
```

This preserves implementation independence.

---

# 16. Streaming

Streaming is a standardized AI Capability.

An implementation may support Streaming when declared as a supported capability.

The initial AI SDK Contract shall therefore allow Streaming as a capability without requiring the core SDK contract to define a specific transport mechanism.

The transport used to deliver streaming data remains an implementation-design concern.

---

# 17. Capability Extensibility

New AI capabilities may be introduced without changing the fundamental AI SDK request envelope.

For example:

```text
AIRequest
├── request_id
├── capability = new_capability
├── input
└── metadata
```

The AI SDK remains stable while the capability-specific contract evolves independently.

This follows the existing capability architecture, which is designed to add future capabilities while preserving existing logical behavior.

---

# 18. Validation Rules

The SDK shall reject a request when:

* `request_id` is missing.
* `capability` is missing.
* Required capability input is invalid.
* The active AI Configuration is unavailable.
* The requested capability is unsupported.

Invalid requests shall be rejected before AI execution.

The SDK shall not silently repair an invalid request in a way that changes its intended meaning.

---

# 19. Fail-Fast Behavior

When a request cannot be safely completed, the SDK shall terminate the request and return a standardized error.

The SDK shall not silently substitute another AI implementation.

Automatic fallback to another implementation is outside this contract unless explicitly established by another platform specification.

---

# 20. Execution Consistency

Equivalent capability requests shall produce equivalent SDK-level behavior regardless of implementation.

The quality or content of AI output may differ between implementations.

However, the following shall remain consistent:

* Request contract.
* Response contract.
* Error contract.
* Capability identity.
* Configuration boundary.
* SDK behavior.

This preserves one programming model across different AI technologies.

---

# 21. Security Contract

The AI SDK shall not permanently own or store user credentials.

Authentication information belongs to the AI Configuration and is handled by the relevant implementation.

The SDK shall not permanently store:

* API keys.
* Access tokens.
* Vendor credentials.
* Runtime authentication secrets.

The SDK may access required configuration information temporarily during request execution.

Executable tasks shall never receive implementation credentials.

---

# 22. Conformance

An AI implementation conforms to this contract when it:

1. Accepts standardized AI SDK requests.
2. Supports one or more standardized capabilities.
3. Produces standardized responses.
4. Produces standardized errors.
5. Respects the active AI Configuration.
6. Hides implementation-specific behavior.
7. Does not require executable tasks to understand its implementation.
8. Preserves the public AI SDK contract.

These requirements align with the existing AI SDK conformance model.

---

# 23. Compatibility

The contract shall remain compatible across:

* Remote AI providers.
* Local AI runtimes.
* Future execution engines.
* Future communication protocols.
* Future AI technologies.

An implementation may evolve internally without requiring consumers to change when the public contract remains compatible.

---

# 25. Contract Principle

The AI SDK Contract follows one fundamental rule:

> **Request capabilities, not implementations.**

The consumer asks PRIDE for an Artificial Intelligence capability.

The active AI Configuration determines the execution target.

The implementation determines how the capability is executed.

The AI SDK determines how the request, response, and error are represented.

This separation allows Artificial Intelligence implementations to evolve without requiring executable tasks to change.
